# Packaging and release

## What gets published

| package | contents |
|---|---|
| `@sudo-ai/iroh-node` | the loader: `index.js`, `index.d.ts`, license files. No binary. |
| `@sudo-ai/iroh-node-linux-x64-gnu` | `iroh-node.linux-x64-gnu.node` |
| `@sudo-ai/iroh-node-linux-x64-musl` | `iroh-node.linux-x64-musl.node` |
| `@sudo-ai/iroh-node-linux-arm64-gnu` | `iroh-node.linux-arm64-gnu.node` |
| `@sudo-ai/iroh-node-linux-arm64-musl` | `iroh-node.linux-arm64-musl.node` |
| `@sudo-ai/iroh-node-darwin-arm64` | `iroh-node.darwin-arm64.node` |
| `@sudo-ai/iroh-node-darwin-x64` | `iroh-node.darwin-x64.node` |
| `@sudo-ai/iroh-node-win32-x64-msvc` | `iroh-node.win32-x64-msvc.node` |

The loader lists the seven platform packages as `optionalDependencies` at its own exact version. Each
platform package declares `os`, `cpu` and (on Linux) `libc`, so a package manager installs only the one
that fits. `index.js` (generated by napi-rs) first looks for `iroh-node.<platform>.node` next to itself,
which is what a local build produces, and then requires the platform package.

The platform package manifests live in `npm/<platform>/package.json` (generated once with
`napi create-npm-dirs`, then committed). Their binaries are not committed: CI puts them there.

## CI (`.github/workflows/build.yml`)

On every push to `main` and every pull request:

1. **build**: seven jobs, one per target. macOS and Windows build natively. linux-x64-gnu uses
   `--use-napi-cross` (the napi-rs cross toolchain, glibc 2.17 baseline). The musl targets and
   linux-arm64-gnu use `-x` (cargo-zigbuild); arm64 glibc is pinned to the same baseline with the target
   spelling `aarch64-unknown-linux-gnu.2.17`. It does not use `--use-napi-cross` because that toolchain's
   gcc cannot assemble ring's aarch64 sources. Each job uploads its `.node` as the artifact
   `bindings-<target>`.
2. **test**: runs `npm test` against the built binary on linux-x64 (glibc), linux-arm64 (glibc),
   darwin-arm64 and win32-x64. The tests need nothing from npm. The compat tests against `@number0/iroh`
   skip themselves there.

On a `v*` tag, additionally:

3. **publish**: downloads all artifacts, moves each into its `npm/<platform>/` directory
   (`napi artifacts`), copies the license files next to it, runs `scripts/check-release.cjs <tag>`, then
   runs `npm publish --provenance --access public` for the seven platform packages and last for the loader.

`scripts/check-release.cjs` refuses the release unless the tag, `package.json`, `index.js`, `Cargo.toml`,
every `npm/*/package.json` and every `optionalDependencies` entry carry the same version, every platform package
holds its binary, and the loader directory holds none.

## One-time setup

1. Create the `sudo-ai` scope (organization) on npmjs.com if it does not exist yet.
2. Create an npm **automation** token (or a granular token with read/write on the `@sudo-ai` scope).
3. Add it to the GitHub repository as the Actions secret `NPM_TOKEN`
   (`gh secret set NPM_TOKEN --repo Matrixx0070/sudo-iroh-node`).

Provenance needs nothing else: the publish job has `id-token: write`, and the repository is public (npm
rejects provenance from private repositories).

## Releasing

```bash
npm version 0.2.0        # or patch / minor / major
git push origin main --follow-tags
```

`npm version` runs the `version` script, which stamps the new version into the platform packages
(`napi version`), the loader's `optionalDependencies`, `Cargo.toml`, `Cargo.lock` and the version check
inside the generated `index.js` (`scripts/sync-versions.cjs`), and adds those files to the version commit. The pushed tag `v0.2.0` starts
the workflow; nothing is published before every build and every test job is green.

A prerelease version (`npm version 0.2.0-rc.1`) is published under the dist-tag `next` instead of
`latest`.

If the publish job fails half way (for example a registry error), re-run it: versions already on the
registry are skipped.

After the first release, run `npm install` once and commit `package-lock.json`: only then can the lock
file record the platform packages. Until they exist on the registry, `npm ci` refuses the lock file, which
is why the workflow installs with `npm install`.

## Local use without the registry

`npm run build` leaves `iroh-node.<platform>.node` next to `index.js`, and the loader's `files` list
includes it. A `file:` dependency on this directory therefore works on the machine that built it:

```json
{ "optionalDependencies": { "@sudo-ai/iroh-node": "file:/root/sudo-iroh-node" } }
```

That is how SUDO-AI consumes the package until it is published.
